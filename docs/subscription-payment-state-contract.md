# 아티메뉴 구독·결제 상태와 실패 복구 계약

기준일: 2026-11-11. 서버 코드와 기존 운영 기록을 대조한 현행 흐름 요약이다. 이번 문서 작업에서는 실카드 청구/환불·고객 계약 수정·Production Cron 실행을 하지 않았다. 환경별 실행 게이트와 실제 외부 결제 결과는 별도로 확인한다.

## 원본과 상태의 소유권

요금·상품/이용권은 [서비스·요금 기준](service-pricing-contract.md)을 따른다. 새 월구독과 과거 연간/개인 체험 계약을 섞지 않고 저장된 계약 금액·기간을 존중한다. 이 문서는 새 요금·환불 정책을 정하지 않는다.

| 상태/기록 | 의미와 확인할 원본 |
| --- | --- |
| 결제사 승인/취소 | PortOne의 실제 결과·통화·금액·처리 ID. HTTP 실패나 내부 `failed`만으로 미승인/미청구라고 단정하지 않음 |
| `orders`, `payments` | 내부 주문·결제 원장. `paid` 행 존재만으로 메뉴/번역/이용권까지 생성 완료라고 보지 않음 |
| `business_subscriptions` | 자동 결제 계약, 상태·저장 금액·주기·기간·다음 결제일·해지 예약. 청구 원장/콘텐츠와 별도 |
| `service_entitlements` | 메뉴판의 실제 서비스 이용 권리·기간·보관 정보. 구독 행의 존재와 동일하지 않음 |
| `menu_sites` 및 콘텐츠 | 메뉴판/스타터·번역·디자인 연결. 결제·구독과 같은 ID로 연결됐는지 확인 |
| `menu_plan_changes` | 고객이 동의한 다음 결제일 이용권 변경 예약과 고정 견적/처리 상태 |
| `refund_requests` | 환불 견적·중복방지·진행/완료/검토 기록. 해지 예약과 별개 |

공통 불변조건은 같은 결제/구독 시도의 소유자·상품·금액·연결 관계가 일치해야 한다는 것이다. UI 성공 문구, 내부 원장, 외부 승인, 이용 권리, 콘텐츠 생성 완료를 각각 확인한다. 단계가 분리돼 있으므로 모든 경로가 하나의 DB 트랜잭션이라고 주장하지 않는다.

## 시작·체험·구매 후 생성

### 월구독 시작

[구독 시작 API](../app/api/business-subscriptions/start/route.ts)는 인증/사업자/상품·디자인/소유권·체험 적격성을 확인한다. 새 시도는 `purchaseAttemptId`에서 고정 최초 결제 ID를 만든다. [중복 판정 helper](../lib/payment-provisioning-idempotency.ts)의 `create`/`return_existing`/`recover`/`manual_review`는 내부 처리 선택이며 고객 구독 상태값이 아니다.

- 적격 30일 체험은 결제수단 등록과 계약/이용권/콘텐츠 생성 후 시작한다. 이 분기에서는 첫 청구를 생략하고 응답 `paymentId`는 `null`이다. 모든 신규 계정에 무조건 체험을 부여하는 규칙이 아니다.
- 유료 시작은 빌링키 승인 확인 후 메뉴 생성/전환, 주문·결제 원장, 구독 활성화·이용권 등 후속 단계를 수행한다.
- 명시적 결제 복구는 기존 `recoverPaymentId`와 `recoverSubscriptionId`를 함께 검증하고 기존 결제의 PAID/금액을 다시 확인하는 경로다. 실패했다고 새 시도 ID로 재결제시키지 않는다.
- 결제 이후 후속 저장이 실패하면 `POST_PAYMENT_PERSISTENCE_FAILED` 등의 단계/코드와 기존 처리 ID를 기준으로 확인한다. 오류 응답은 카드 결제 취소를 뜻하지 않는다.

### 일반 결제 완료

[결제 완료 API](../app/api/payment/complete/route.ts)는 기존 완료 결과를 우선 찾고, 결제 검증·메뉴 생성/복구·주문·결제·이용권·첫 메뉴 크레딧 처리 등을 수행한다. 월 자동결제 상품은 이 API 대신 빌링키 경로로 보낸다. 새 요청의 생성 충돌은 같은 결제 완료 결과를 다시 확인한다.

결제 원장은 있지만 연결 메뉴판이 없거나 주소 충돌 등 검토 대상이면 자동 새 구매로 처리하지 않는다. [구매 스타터 서비스](../lib/server/purchased-menu-provisioning.ts)는 기존 스타터가 있을 때 페이지/카테고리/아이템과 번역을 확인한다. 부분 생성이면 자동 덮어쓰기를 중단하고 관리자 확인을 요구한다. 준비된 스타터 네 언어는 [번역 계약](starter-translations-qa.md)에 따라 미리보기와 신규 구매에 함께 들어간다.

## 갱신·해지·이용권 변경

| 흐름 | 현행 동작 | 실패/재시도 경계 |
| --- | --- | --- |
| 기존 계약 갱신 | [구독 Cron](../app/api/cron/process-subscriptions/route.ts)은 `active`이며 다음 결제일이 지난 대상을 조회. 저장 계약 금액을 우선하고 해당 기간의 고정 결제 ID 사용 | 승인→내부 원장→기간/이용권 갱신이 별도 단계. 기존 원장이 있으면 `skipped_duplicate`일 수 있어 미완료 기간 갱신까지 자동 복구됐다고 보지 않음 |
| 기간 말 해지 | [구독 관리 서비스](../lib/server/business-subscription-management-service.ts)의 `cancel_at_period_end` 예약. 갱신은 카드 키 검사보다 이 플래그를 먼저 처리해 기간 말 만료 | 해지 예약은 즉시 환불/콘텐츠 삭제가 아님. 예약 취소는 취소 플래그 해제이며 만료 뒤 서비스 복구와 다름 |
| 다음 결제일 이용권 변경 | [전환 절차](runbooks/menu-plan-change-reservations.md), [전환 서비스](../lib/server/menu-plan-change-service.ts)의 고정 견적/결제 ID와 확정 RPC 사용 | 고객의 명시적 선택만 적용, 중간 차액/기존 계약 자동 이관 없음. 처리 실패 시 종전 금액 청구로 우회하지 않음. 처리 중 예약 수정/취소/해지는 보호 경계 확인 |
| 보관/정리 | 체험 만료·기간 종료·결제 문제별 이용권/보관 기준과 Cron 단계 | [보관 정책](../lib/service-retention-policy.ts), [영구 삭제 절차](service-lifecycle-hard-delete-runbook.md) 참조. 보관/만료를 실제 파일/계정 삭제와 혼동하지 않음 |

**기존 갱신의 남은 한계:** 갱신 처리의 catch는 결제사 오류뿐 아니라 후속 원장/기간 저장 오류도 포함하고 `past_due`로 표시한다. 코드에 유예기간 종료·자동 재시도·고객 안내 정책 TODO가 남아 있다. 결제 실패 알림 경로는 있지만 전체 연체 복구 정책 완료를 뜻하지 않는다. `past_due`가 일반 `active` 갱신 조회에 자동 재진입한다고 설명하지 않는다. 외부 결제가 이미 성공했는지 먼저 확인한 뒤 승인된 동일 건 복구를 진행해야 한다.

실행 스위치는 현재 코드/실환경을 함께 확인한다. 새 이용권 변경 처리의 `MENU_PLAN_CHANGE_LEDGER_READY`·`ENABLE_MENU_PLAN_CHANGE_RENEWALS`와 기존 갱신 실행은 별도다. [실행 판정](../lib/menu-plan-change-cron-policy.ts)은 GET과 명시적 POST dry-run을 구분한다. 오래된 운영 기록의 ON/OFF를 오늘의 실설정으로 재사용하지 않는다.

## 환불·보관 메뉴판 복구

[연간 환불 서비스](../lib/server/yearly-refund-service.ts)는 견적과 확인을 분리하고 `refund_requests`의 중복방지 키·결제사 취소·내부 확정을 다룬다. `needs_review`는 외부 결과/저장 상태 확인이 필요한 결과이며 새 환불 요청으로 우회하지 않는다. 이 경로의 지원 대상을 모든 새 월구독에 일반화하거나, 구독 해지 예약을 환불 완료로 안내하지 않는다.

[보관 복구 서비스](../lib/server/menu-site-restore-service.ts)는 소유 메뉴, 보관 상태·남은 보관 기간·활성 이용권/구독·진행 중 환불 등을 사전 확인한 뒤 복구 결제/계약 경로로 진행한다. 이것은 남아 있는 메뉴판의 서비스 복구이며, 이미 삭제된 콘텐츠나 Storage 파일을 DB 백업에서 되살리는 [장애 복구](runbooks/backup-disaster-recovery.md)와 다르다.

## 부분 실패 확인표

| 관찰 상태 | 먼저 확인할 것 | 조치 기준 |
| --- | --- | --- |
| 요청 timeout/오류, 외부 결과 불명 | 같은 결제 ID의 결제사 상태·금액·소유 계약 | ‘실패=미청구’로 보고 새 결제 ID를 만들지 않음 |
| 외부 PAID, 메뉴/원장/이용권 일부 없음 | 기존 시도/구독/메뉴 연결과 단계별 저장 상태 | 지원되는 동일 건 복구를 사용. 소유권/금액/부분 스타터 오류는 검토 후 처리 |
| 내부 `paid`, 메뉴 연결 없음 | 상품 유형·원장·구독·이용권·크레딧 이행 | 계정 단위 AI 충전은 메뉴 연결이 없을 수 있음. [불완전 결제 감사](runbooks/incomplete-payment-order-audit.md)의 분류 기준 사용 |
| 기존 갱신 `past_due` 또는 `skipped_duplicate` | 결제사 승인, 주문/결제 존재, 실제 갱신 기간·이용권 | 중복 청구 방지와 갱신 완료는 별개. 현재 자동 복구 보장 없음 |
| 예약 이용권 변경 `processing`/검토 오류 | 예약의 고정 결제 ID·PAID·견적·최신 메뉴 snapshot | 기존 확정/재처리 경로 사용. 임의 구독 SQL/옛 금액 청구/자동 환불 금지 |
| 환불 `needs_review` | 외부 취소 금액/결과·내부 요청/원장 상태 | 외부 취소를 새로 보내기 전에 기존 결과 확인 |
| 알림 발송 실패 | 서비스 이행·결제 완료 여부와 알림 전달 상태 | 알림 오류를 이유로 청구/메뉴 생성을 다시 실행하지 않음 |

고객에게 새 결제/환불을 요구하거나 운영 DB를 수정하기 전에 대상 건·현재 상태·기존 처리 ID·예정 수정·외부 영향이 확인된 복구 계획을 만든다. 문서/테스트가 실제 청구·환불·고객 데이터 변경을 승인하지 않는다. 비밀키·카드 키·개인정보·원문 payload를 MD/공개 로그에 넣지 않는다.

## 검증 범위와 남은 일

관련 단위/모의 검사: `lib/payment-provisioning-idempotency.test.ts`, `lib/subscription-renewal-policy.test.ts`, `lib/menu-plan-change-policy.test.ts`, `lib/menu-plan-change-cron-policy.test.ts`, `lib/starter-translation-parity.test.ts`. 전환의 격리 DB/모의 결제 검증은 [기존 전환 절차](runbooks/menu-plan-change-reservations.md)에 실행일과 환경을 구분해 기록돼 있다.

이번 문서 작업에서 현재 코드의 흐름/한계와 관련 검사를 대조했다. 실제 카드 승인 후 저장 실패·환불 후 저장 실패·동시 갱신의 Production 종단 검증, 환경별 실행값 재확인, 기존 갱신 자동 재시도 정책의 결정/구현은 별도 남은 범위다. 과거 검사 통과나 migration 파일 존재를 이 범위의 완료 증거로 쓰지 않는다.
