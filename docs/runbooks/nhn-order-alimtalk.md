# NHN 조리완료 알림톡 연동

## 적용 범위

NHN Cloud KakaoTalk Bizmessage API v2.3용 구현이다. 미배포 SENS 초안의 주문 리스트·테이블 상세 발송 UI를 현재 주문 관리 화면에 연결했다. 기존 결제 단말 작업과는 별도 브랜치다.

현재 구현은 매장별 소유자 인증 채널과 고정 안내 템플릿을 사용한다. 채널 인증 후 안내 템플릿 준비를 자동으로 이어간다. 아티메뉴 채널이나 과거 검수용 환경변수를 다른 매장의 기본 발신자로 사용하지 않는다. 일반 고객 발송은 전역 게이트와 매장 발송 플래그로 계속 차단한다. 잔액 충전·과금은 별도 단계이며 아래 날짜별 기록은 당시 상태를 보존한다.

## 서버 설정

| 환경변수 | 값 |
| --- | --- |
| `ORDER_ALIMTALK_ENABLED` | 기본 미설정. 승인·실수신 검수 시에만 `true` |
| `ORDER_ALIMTALK_MENU_SITE_ID` | 승인된 기존 채널 복구 전용 메뉴판 UUID. 실제 발송 라우팅에는 사용하지 않음 |
| `ORDER_ALIMTALK_NHN_APP_KEY` | 아티메뉴 프로젝트의 KakaoTalk Bizmessage Appkey |
| `ORDER_ALIMTALK_NHN_SECRET_KEY` | 같은 서비스의 Secret Key |
| `ORDER_ALIMTALK_NHN_SENDER_KEY` | 승인된 기존 채널 복구 전용. 실제 발송은 DB의 매장별 발신 키 사용 |
| `ORDER_ALIMTALK_NHN_CHANNEL_ID` | 승인된 기존 채널 복구 전용 검색용 ID |
| `ORDER_ALIMTALK_NHN_TEMPLATE_CODE` | 과거 검수용 값. 현재 고정 템플릿 코드는 서버 계약 `cooking_ready_v1` |
| `ORDER_ALIMTALK_NHN_EXISTING_OWNER_ID` | 기존 발신 프로필 연결을 별도 승인한 테스트 메뉴판 사장님의 사용자 UUID. 미설정이면 기존 프로필 연결 불가 |

모든 값은 서버 전용이다. `NEXT_PUBLIC_`을 붙이거나 Git·채팅에 키 값을 넣지 않는다. 실제 키 생성/권한 추가는 사용자가 NHN 콘솔에서 확인한다. 키를 저장한 것만으로 발송되지 않으며 활성화 값과 메뉴판 연결이 모두 필요하다.

## 발송 문구와 데이터

기본형·강조 없음·버튼 없음으로 승인된 템플릿만 사용한다. 매번 NHN 템플릿 조회에서 채널·발신 키·코드·승인 상태(`TSC03`)·차단·휴면 상태를 확인한다. 승인된 본문에 실제로 사용한 변수만 치환 발송 API에 전달한다.

```text
[#{매장명}] 조리완료 안내

주문하신 메뉴가 준비되었습니다.

룸: #{룸명}
테이블·키오스크: #{테이블명}
주문번호: #{주문번호}

매장 직원의 안내에 따라 음식을 받아주세요.
```

- 매장명: 고객 메뉴판과 동일한 `restaurant_name → business_name → name` 우선순위.
- 룸/테이블: 주문이 이동했다면 현재 `service_table_id`, 아니면 `menu_table_id`. 해당 메뉴판으로 범위를 제한하여 실제 이름과 저장된 배치도 소속을 읽는다. 과거 소속 없는 항목은 `룸 미지정`으로 표시한다. 조회 실패 시 발송하지 않는다.
- 주문번호: 서버에 저장된 `order_number`. 고객이 전달한 표시 값을 신뢰하지 않는다.
- 수신 번호: 주문 시 저장된 `notification_phone`만 사용한다. 클라이언트에는 마스킹한 번호만 보낸다.
- 첫 사용자 제한이 걸린 프로필은 변수 길이 제한 때문에 실패할 수 있다. 매장명을 임의로 잘라 보내지 말고 NHN 프로필 제한과 실수신을 확인한다.

## 상태·권한·중복 방지

- 주문 조회/처리 권한과 활성 운영 화면 조건을 서버에서 확인한다. 발송은 연락처가 있는 `ready` 주문에만 허용하며, 템플릿 확인 후 다시 주문 상태를 읽는다.
- 발송 이력 테이블은 RLS와 권한 회수로 일반 로그인·비로그인 클라이언트의 직접 접근을 차단한다. 서비스 역할은 select/insert/update만 사용한다.
- 주문별 시도 번호 유일성과 한 개의 pending 시도만 허용하는 부분 유일 인덱스로 동시 클릭을 막는다. 재발송은 서버에서 최신 시도 ID를 비교하고 새 시도를 기록한다.
- DB에 제출 시작을 먼저 기록하고 시도 UUID를 NHN `X-NC-API-IDEMPOTENCY-KEY`로 전달한다. 접수 성공은 완료가 아닌 pending이다. NHN requestId와 recipientSeq를 함께 저장하여 정확한 수신 결과를 조회한다.
- `COMPLETED` + 결과 코드 `1000`만 발송 완료로 표시한다. HTTP/API 접수 코드 `0`과 카카오 최종 수신 결과를 혼동하지 않는다. `FAILED`/`CANCEL`은 실패, 그 외는 확인 중이다. 결과 조회의 주문·발신 키·템플릿이 일치해야 상태를 갱신한다.
- 타임아웃·접수 응답 유실·DB 저장 실패는 자동 재발송하지 않는다. 요청 시작 전 실패한 시도만 60초 뒤 안전하게 실패로 돌릴 수 있다. 시작 후 접수 번호를 잃은 경우 NHN 발송 결과 조회에서 확인한다.
- SMS 대체 발송을 명시적으로 끈다. 알림톡 성공·실패·재발송은 주문 상태나 결제 상태를 변경하지 않는다. 픽업·서빙 완료는 직원이 별도 처리한다.
- 진행 중인 시도가 있는 동안 발신 키·프로젝트·템플릿 연결을 바꾸지 않는다.

## 검수 및 출시 순서

1. `node --import tsx --test lib/order-ready-alimtalk-provider.test.ts`로 승인 대기/잘못된 채널/차단/변수 오류/중복키/접수·성공 구분을 검수한다.
2. 개발 전용 `http://127.0.0.1:3136/qa-alimtalk-local`에서 모의 발송한다. #201 성공, #202 실패 후 재발송, #203 연락처 없음, #204 조리중 조건을 확인한다. 실제 고객 발송·운영 DB 쓰기는 없다.
3. SQL `20261125041134_add_nhn_order_alimtalk_attempts.sql`은 로컬 Postgres(PGlite)의 최소 주문 스키마에서 RLS·일반 사용자 접근 차단·중복 pending·재시도·연락처/서빙 조건을 확인했다. 운영 적용은 별도다.
4. 템플릿 승인과 사용자의 키 준비 후 운영 DB 적용 및 배포 승인을 받아 적용한다. 지정 테스트 메뉴판과 수신 동의 번호로 실제 발송·결과 확인·실패·재발송·픽업 분리를 확인한 뒤 운영 발송을 연다.

2026-11-25 인증 확인: 사용자 승인으로 테스트 메뉴판 `261113test`의 ID를 읽고 로컬 전용 설정에 연결했다. 저장된 Appkey·Secret Key·발신 키로 NHN 템플릿 GET 조회가 HTTP 200, `isSuccessful=true`, `resultCode=0`을 반환했다. 채널·발신 키·템플릿 코드가 모두 일치했고 기본형/강조 없음, 차단·휴면 없음, 변수 4개가 확인됐다. 템플릿은 `TSC02`(검수 중)였다. 실제 v2.3 응답의 단건 객체는 문서 예시의 `templates`와 달리 `template`으로 반환되어 두 형식을 모두 처리하도록 수정하고 테스트를 추가했다.

실제 인증 키와 메뉴판 연결 값은 Git에서 제외된 `.env.development.local`에만 저장한다. `ORDER_ALIMTALK_ENABLED=false`를 유지했고 SELECT와 템플릿 GET 외 요청은 하지 않았다. 운영 DB 적용·실제 발송·운영 배포는 아직 하지 않았다.

## 점주 채널 직접 연결 (로컬 구현, 2026-11-25)

위치: 매장 운영 → 주문 설정 → 조리완료 알림톡. 사장님이 검색용 채널 ID, 채널 관리자 휴대폰 번호, 업종 대·중·소분류를 입력하고 카카오톡 인증번호 6자리로 연결한다. 직원에게는 변경 권한을 주지 않는다. 모든 서버 액션은 세션·매장 소유권·쓰기 가능 상태를 다시 확인한다.

사용하는 NHN API는 `GET /sender/categories`, `POST /senders`, `POST /sender/token`이다. 업종 응답의 중·소분류 `code`는 실제로 4자리 구간 값으로 내려와 부모 코드를 붙여 11자리로 만든다. OTP 검증은 요청한 채널과 `YSC03` 상태, 40자리 발신 키가 일치해야 성공으로 저장한다. 이미 등록된 프로필(-1004)을 ID만으로 가져오거나 인증을 우회하지 않는다. 별도로 승인한 기존 프로필 연결은 아래의 제한된 복구 경로를 사용한다. 임의의 채널 인수·변경·연결 해제는 포함하지 않는다.

- 신규 SQL: `20261125045027_add_merchant_alimtalk_channels.sql`. **운영에는 미적용**. UI·서버 기능도 미배포다.
- 테이블/RPC는 일반 비로그인·로그인 역할에 모두 비공개다. 서버만 발신 키를 읽고 저장하며, 클라이언트 응답은 채널·상태·마스킹 번호·일자·남은 횟수만 포함한다. 원문 휴대폰 번호와 인증번호는 저장하지 않는다.
- 60초 재요청 간격, 점주 전체 메뉴판 합산 1시간당 최대 10회, 인증 유효시간 10분, 요청당 최대 5회 검증을 적용한다. DB 예약과 유일 인덱스로 동시 요청·다른 메뉴판의 활성 채널 중복을 차단한다. 이전 소유자의 인증은 새 소유자에게 승계하지 않는다.
- 현재 연결 단위는 메뉴판당 채널 1개다. 동일 채널의 여러 메뉴판 공유나 채널 교체는 별도 흐름이 필요하다. 만료된 미인증 예약은 새 인증 요청으로 교체할 수 있다.
- 연결 성공 후에도 `sending_enabled=false`이며 DB CHECK로 활성화를 막는다. 기존 발송 환경변수도 `ORDER_ALIMTALK_ENABLED=false`를 유지한다. 점주 채널 연결 데이터는 기존 테스트용 발송 설정을 자동 변경하지 않는다.
- NHN 프로젝트 Appkey/Secret Key만으로 업종 조회·인증 연결을 준비할 수 있다. 실 발신 키·템플릿 승인·발송 활성화와 분리되어 있다.
- 인증 요청 응답이 유실되면 새 요청을 자동 반복하지 않고 번호를 받은 점주가 인증을 이어갈 수 있게 한다. NHN 인증 후 DB 저장이 실패한 경우 임의로 기존 키를 붙이지 않고 고객지원 확인으로 중단한다.

## 이미 인증한 발신 프로필 연결 보완

사용자가 직접 NHN 콘솔에서 인증한 `@아티메뉴`를 승인된 테스트 메뉴판 `261113test`에 연결하기 위한 경로다. 서버에 고정한 메뉴판 UUID·소유자 UUID·채널 ID·발신 키가 모두 일치할 때만 ‘기존 채널 연결’ 버튼과 액션을 허용한다. 단순히 공유 NHN 프로젝트에 프로필이 존재하거나 점주가 채널 ID를 알고 있다는 이유로 연결하지 않는다. 일반 점주의 새로운 채널은 인증번호 절차를 그대로 거친다.

- `GET /senders/{senderKey}`로 정확한 채널 ID·발신 키·정상 등록(`YSC03`)·카카오 정상(`A`)·프로필 활성(`A`)·휴면/차단 없음·업종 11자 코드를 재확인한다. 등록·삭제·인증번호 요청 API를 호출하지 않는다.
- 서버 액션에서 소유자·매장 쓰기 권한을 확인하고, 외부 조회가 끝난 뒤 DB RPC에서 최신 소유자를 잠금과 함께 다시 검증한다. 소유자가 바뀌면 이전 승인 값을 승계하지 않는다.

## 매장별 실제 발송 연결

- 채널 인증 완료 액션에서 안내 템플릿을 자동 준비한다. 기존 연결은 ‘메시지 준비’로 시작한다. 일반 화면 로딩은 NHN 등록 요청을 보내지 않는다.
- 고정 문구는 실제 승인된 `cooking_ready_v1`의 본문·기본형·강조 없음·버튼 없음과 동일하다. 템플릿 분류는 승인된 `002001`이다. 점주가 문구를 바꾸는 입력란은 없다.
- 해당 매장 발신 프로필과 템플릿 목록·단건을 읽어 정확한 채널·발신 키·본문을 대조한다. 기존 동일 코드를 덮어쓰지 않는다. 다른 문구, 반려, 차단·휴면, 불명확한 응답은 구분해 중단한다.
- 등록 POST 전에 DB에 제출 시작을 기록한다. 응답 유실 시 자동 재등록하지 않고 조회만 한다. 10초 요청 간격, 45초 검사 임대와 검사 UUID로 경쟁 요청·늦은 저장을 막는다.
- 심사 중 열린 화면에서는 30초마다 읽기 전용 승인 확인을 한다. 이 조회는 템플릿을 새로 등록하지 않고 반복 토스트도 만들지 않는다. 승인을 확인하면 자동 조회가 끝난다.
- 발송 설정은 `menu_alimtalk_channels`와 현재 메뉴판 소유자를 대조해 매장별로 정한다. 전역 OFF, 매장 OFF, 연결 미완료, 소유자 변경, 미승인/변경된 문구는 제출 전에 차단한다. 실제 POST 직전에도 주문·연락처·채널을 재확인한다.
- 시도 이력에 발신 키·채널·템플릿·채널 소유자·프로젝트 Appkey의 SHA-256 지문을 저장한다. 결과 확인은 현재 바뀐 채널이 아닌 발송 당시 연결을 사용한다. 소유자나 NHN 프로젝트가 달라지면 외부 조회를 중단한다. 비밀 키나 원본 Appkey는 이력과 클라이언트에 저장하지 않는다.
- 기존 최종 완료 이력은 그대로 보존한다. 운영 적용 전 미해결 pending 시도가 없는지 확인한다.
