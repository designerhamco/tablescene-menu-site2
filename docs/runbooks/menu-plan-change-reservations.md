# 기존 구독의 다음 결제일 이용권 전환

사용자 승인 정책(2026-10-21): 고객이 직접 변경을 선택한 경우에만 **다음 결제일부터** 새 요금·이용권을 적용한다. 중간 차액·즉시 청구·자동 기존 계약 이관은 없다.

## 운영 적용 상태

- 사용자에게 새 파일 1건의 운영 적용·전환 활성화 승인을 받은 뒤 `20261021140627_add_menu_plan_change_reservations.sql`을 운영 `tablescene-prod`에 정확히 1회 적용했다. PR #295는 `ceb13a4277421a83d16511556f4ff29742965388`로 병합했다. 이전 계약 SQL과 별도 파일이며 일괄 migration 실행은 하지 않았다.
- `MENU_PLAN_CHANGE_LEDGER_READY`·`ENABLE_MENU_PLAN_CHANGE_RENEWALS`·`ENABLE_MENU_PLAN_CHANGES`가 모두 true일 때만 신규 예약을 받는다. 코드 기본값은 미설정/OFF이며, 이번 승인 범위의 Production 세 값은 true로 설정했다. Preview/Development와 다른 기능 활성화 설정은 변경하지 않았다. 신규 예약의 결제 실행은 기존 자동청구 설정과 분리해 신청한 전환 건만 처리한다. 기존 갱신 cron의 실행 승인 스위치·실카드 설정은 변경하지 않는다.
- 실제 고객 계약·청구·환불·예약 행은 검사를 위해 변경하지 않았다. 로컬 검수는 임시 DB와 모의 결제사를 사용하고, 운영 검수는 읽기 및 명시적 POST dry-run만 실행한다.

## 고객 흐름

마이페이지 → 구독 관리 → 이용권 변경. 같은 서비스의 기본 디자인/디자인 포함 이용권과 적용할 디자인을 고른다. 적용일·월요금·부가세·디자인을 확인하고 체크해야 예약된다. 기본 이용권으로 낮출 때는 기본 디자인만 선택할 수 있다.

- 현재 요금과 디자인 사용은 적용일까지 유지한다. 결제가 성공하면 새 계약·디자인·이용권·영수증이 함께 확정된다. 메뉴·사진·분류·공개 주소는 유지하며, 디자인별 스타일도 기존 스냅샷으로 보존한다.
- 월결제 전환 상품임을 표시한다. 기존 연결제는 이미 결제한 연간 기간을 모두 유지한 뒤 **다음 연간 결제 예정일**부터 월결제로 전환하며 중도 정산을 하지 않는다.
- 접수 시점의 공개 프로모션을 서버에서 계산한다. 해지 없이 유지 중인 식별 가능한 새 이용권 얼리버드 계약은 업/다운그레이드에도 같은 할인 유형을 유지한다. 견적 금액은 예약에 고정하고 이후 가격표 숫자 변경으로 다시 계산하지 않는다.
- 결제 처리 전 예약 수정·취소가 가능하다. 해지 예약은 이용권 변경 예약을 함께 취소한다. 해지 예약 취소가 과거 이용권 변경을 되살리지는 않는다.
- 서버의 적용일·금액·주기·버전과 고객이 확인한 값이 다르면 저장하지 않는다. 화면은 새 안내를 읽어 다시 동의하도록 한다.

## 저장과 갱신

`menu-plan-change-policy.ts`가 소유 메뉴 연결·구독 상태·서비스·디자인 범위·견적·동의를 검증한다. API는 실제 인증 사용자만 사용하며 다른 출처의 쓰기 요청을 차단한다. 고객에게 카드 키는 반환하지 않는다.

`menu_plan_changes`는 서버 전용 RLS 예약 원장이다. authenticated/anon의 테이블·RPC 권한은 없으며 보안 invoker RPC는 service_role만 실행한다. 기존 구독·금액은 backfill하지 않는다. 예약 생성/취소/claim/확정은 같은 구독 행 잠금 순서를 사용한다.

갱신 시 새 견적 금액과 결제 ID를 DB에서 고정한다. 기존 PortOne 어댑터가 정확한 ID·금액·PAID를 검증한다. 같은 처리의 재시도는 같은 결제 ID를 사용한다. 메뉴 편집 충돌 시 최신 내용으로 디자인 변경을 다시 계산하며, 영수증·새 계약·연결 이용권·디자인을 한 트랜잭션으로 확정한다. 실패하면 종전 금액으로 다시 청구하지 않는다. 결제 후 저장 실패도 같은 ID로 재확인·확정하며 로그의 구독 ID로 예약을 확인할 수 있다. 처리 중 예약의 수정·취소·구독 해지는 막는다.

기존 구독에 예약이 없으면 종전 저장 계약 금액 갱신 경로를 그대로 사용한다. 기존 처리에서의 자동 재시도/연체 보관 정책을 일괄 바꾸지 않는다. 신규 예약 처리 실패는 처리 상태를 유지하고 검토 코드로 보고한다. 새로운 결제 ID를 만들어 재청구하거나 임의 환불하지 않는다.

## 적용 순서와 복구

1. 코드·임시 DB·브라우저 검증을 끝낸 뒤 위 SQL 파일 한 건에 대한 운영 승인을 받는다. 적용 직전 기존 구독 수·금액 합계/지문·계약 필드를 읽기 전용으로 기록한다.
2. 승인한 파일 한 건만 한 번 실행한다. 과거 migration 재실행/일괄 db push를 하지 않는다. 새 테이블/인덱스/RLS/함수 권한·기존 금액 보존·Security Advisor·서비스 API 접근을 확인한다.
3. 검증한 코드의 운영 배포 성공을 확인하고 `MENU_PLAN_CHANGE_LEDGER_READY=true`로 원장 처리 경로를 켠다. 신규 예약과 신규 예약 결제 실행은 아직 OFF로 두고 명시적 POST dry-run에서 기존 요금 유지와 예약 없음 상태를 확인한다.
4. `ENABLE_MENU_PLAN_CHANGE_RENEWALS=true`로 신청한 전환 건의 결제 처리만 준비한 뒤 `ENABLE_MENU_PLAN_CHANGES=true`로 고객의 명시적 예약을 받는다. 기존 `ENABLE_SUBSCRIPTION_CRON_EXECUTE` 값은 유지한다. GET 스케줄은 두 종류의 실행을 분리하며 POST dry-run은 새 처리도 읽기 전용이다. 응답은 전체 실행과 legacy/new 실행을 각각 보고한다. 실제 카드 청구·환불을 검수 목적으로 실행하지 않는다.
5. 신규 접수 중단은 `ENABLE_MENU_PLAN_CHANGES=false`만 사용한다. 원장 처리는 계속 켜두어 이미 고객이 동의한 예약을 예정대로 처리하고 조회·취소를 제공한다. live 예약이 있는 상태에서 원장 스위치를 끄거나 예전 cron 코드로 롤백하면 안 된다. 먼저 pending/processing을 점검하고 별도 운영 결정을 받는다.

결제 후 적용 확인이 필요한 항목은 `menu_plan_changes`의 processing·payment_id와 결제사 PAID/금액을 읽어 확인한다. 새 결제 ID·자동 환불·임의 SQL로 계약을 직접 바꾸지 않는다. 위 확정 RPC와 최신 메뉴 스냅샷으로 동일 결제 건을 재처리한다.
