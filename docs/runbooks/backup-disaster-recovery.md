# 아티메뉴 백업·장애 복구 운영 절차

기준일: 2026-11-11. **실행 전 운영값 확인이 필요한 절차 문서**다. 저장소의 데이터 경계와 Supabase 공식 안내를 대조했다. 이번 문서 작업에서 Production 백업 설정 조회·파일 반출·복구·결제·Cron 실행은 하지 않았다. 아래 미확인 값을 채우기 전에는 복구 가능 시점/시간을 보장하지 않는다.

## 복구 범위

| 대상 | 복구에 필요한 것 | 주의점 |
| --- | --- | --- |
| Database | 실제 백업/PITR 복구점, 스키마·데이터·권한·사용자 정의 함수/트리거 | 저장소 migration 목록만으로 원격 DB 전체를 재구성했다고 판단하지 않음 |
| Storage | `menu-images`, `menu-videos`의 파일 bytes, bucket/path·크기·형식·검증값 목록, bucket 설정·정책 | DB의 URL/path·객체 메타데이터와 파일 bytes는 별도 |
| Auth | 선택한 복구 방식에 포함되는 계정 데이터, Auth 설정·redirect·메일 설정, 세션 처리 결정 | DB 복구만으로 새 프로젝트의 인증 설정이 완성되지 않음 |
| 앱·외부 연동 | 배포 revision, 환경별 설정 이름/보관 위치, 도메인·메일·결제 연동과 예약 작업 | 비밀값은 별도 승인된 비밀 저장소에서 취급. MD/로그에 복사하지 않음 |
| 외부 결제/전송 | 결제사 승인·취소 결과, 이미 접수/전송된 주문·호출·알림의 처리 결과 | DB를 과거로 돌려도 외부 청구·환불·기기 동작은 취소되지 않음 |

Supabase의 [DB 백업 안내](https://supabase.com/docs/guides/platform/backups)에 따르면 **Storage 파일의 실제 bytes는 DB 백업에 포함되지 않는다.** 파일을 삭제한 뒤 DB만 복구해도 사진/영상은 돌아오지 않는다. 복구 시 선택한 시점 이후 DB 변경은 소실될 수 있고 중단 시간이 발생한다.

[새 프로젝트 복구 안내](https://supabase.com/docs/guides/platform/clone-project)는 DB 복제와 Storage·Auth 설정 등의 재설정을 구분한다. [CLI 백업·복구 안내](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)는 별도 DB/Storage 이전 절차를 제공한다. 사용 가능한 방식과 지원 범위는 실행할 때 다시 확인한다. 공식 예제의 일괄 파일 덮어쓰기를 Production에 그대로 실행하지 않는다.

## 실행 전 운영 기록표

이 표는 승인된 운영값을 기록할 자리다. 임의의 보존 기간·복구 목표를 새 정책으로 확정하지 않는다. 현재 저장소만으로는 다음 실설정을 확인하지 못했다.

| 확인 항목 | 현재 상태 | 남길 증거 |
| --- | --- | --- |
| 담당자·대체 담당자·복구 승인자 | 미확인 | 역할과 접근 권한 확인일 |
| Production 대상·리전·요금제·복구 대상 | 미확인 | 비밀값 없는 환경 식별 및 확인일 |
| DB 일일 백업/PITR 사용 여부·보존·최근 성공 | 미확인 | Dashboard의 복구 가능 범위·성공 시각 |
| Storage 사본 위치·버전·주기·보존·최근 성공 | 미확인 | 접근 통제된 manifest와 검증 결과의 위치 |
| 허용 데이터 손실 범위(RPO) | 미확정 | DB/파일 각각의 목표와 승인일 |
| 목표 복구 시간(RTO) | 미확정 | 재개 범위, 목표와 훈련 실측 시간 |
| 비밀 설정 복원·회수 권한 | 미확인 | 저장소 위치/담당 역할만 기록 |
| 최근 격리 복구 훈련 | 미실행 | 아래 검증표와 결과 기록 |

DB/Storage 사본은 같은 복구 기준 시점과 연결한다. 파일 manifest에는 필요한 bucket/path, 사본 버전, bytes/검증값, 성공/누락 수를 보관하되 원본 고객 파일과 함께 접근 통제한다. DB 백업과 파일 사본의 시점이 다르면 덮어쓴 파일·삭제한 파일·아직 참조되지 않은 파일을 구분해 불일치 범위를 기록한다. 백업은 원본 장애와 같은 권한/삭제 동작에 함께 소실되지 않도록 보관 방식을 검토한다.

보존·삭제 기준은 [데이터 안내](../supabase-data-lifecycle-guide.md), [삭제 절차](../service-lifecycle-hard-delete-runbook.md), [약관·개인정보 검토 현황](../legal-policy-review.md)과 대조한다. 백업을 이유로 무기한 보관하거나, 파기 대상 데이터를 복구 후 다시 공개하지 않는다.

## 장애 발생 시 순서

1. **대상과 영향 확정**: 발생/탐지 시각, 앱 배포 revision, DB 장애/오삭제/파일 유실/권한 문제/외부 결제 불일치를 구분한다. 로그·집계·복구 전 상태를 보존한다. 단순 화면 오류를 이유로 DB 전체를 되돌리지 않는다.
2. **추가 쓰기 통제 결정**: 승인된 운영자가 편집·주문/호출 접수·업로드·자동 청구·삭제·알림 실행의 영향 범위를 정한다. 화면만 닫고 백그라운드 실행까지 중단됐다고 추정하지 않는다. 이 문서는 이미 작동하는 통합 ‘복구 모드’가 있다고 가정하지 않는다. 중단/재개할 경로와 실제 조치를 사건 기록에 남긴다.
3. **복구점 선택**: 장애 직전의 유효한 DB 복구점과 대응하는 파일 사본을 찾는다. 현재 상태를 보존하고, 선택 시점 이후 손실/재대조 대상과 예상 중단 범위를 확인한다. 접근권한·비용·대상 환경과 복구 계획을 승인받는다.
4. **격리 환경에서 먼저 복구**: 가능하면 별도 프로젝트/격리 대상에 복구한다. 고객 공개 도메인, 운영 결제 키, 실제 메일 발송, 기기 연결, 예약 실행을 연결하지 않는다. 백업에 포함된 SQL 작업/트리거 등 자체 실행 경로도 점검한다. DB 복구 완료 알림만으로 재개하지 않는다.
5. **파일 복구와 참조 대조**: 승인된 사본을 Storage API/지원되는 도구로 복원한다. `storage.objects` 행을 SQL로 만드는 것만으로 파일을 복구했다고 보지 않는다. 실제 파일 열림·bytes/검증값·bucket 정책과 DB 참조를 함께 검증한다. 새 프로젝트 URL/path 변경, 가져오기/연결로 다른 메뉴판이 참조하는 파일도 확인한다.
6. **권한·외부 상태 대조**: 아래 검증표를 수행한다. 특히 복구 시점 이후의 실제 결제/환불과 내부 주문·결제·구독·이용권을 같은 처리 ID로 대조한다. 새 결제 ID 생성·청구 재실행·임의 환불로 맞추지 않는다. 모르는 결과는 수동 검토에 남긴다.
7. **운영 전환과 단계별 재개**: 격리 검증 결과, 남은 불일치, 예상 손실, 되돌림 계획을 검토한 뒤 승인된 범위만 전환한다. 공개 읽기 → 인증/편집 → 접수/연동 → 예약 작업 순서로 상태를 확인한다. 고객 동의가 남은 이용권 변경 예약은 [전환 절차](menu-plan-change-reservations.md)의 별도 실행 게이트와 상태를 확인한다.
8. **사후 확인**: 오류/접수/청구/파일 누락을 관찰하고 실제 복구 시간과 잃은 데이터 범위를 기록한다. 복구용 임시 자원·사본은 승인된 보관/파기 절차로 정리한다. 해결하지 못한 항목을 PASS로 닫지 않는다.

## 격리 복구 검증표

| 확인 대상 | 통과 기준 |
| --- | --- |
| 데이터 구조/참조 | 메뉴판→페이지→카테고리→아이템, 가격·칩·기간할인·위젯·번역 참조와 행 수가 복구 기준 manifest에 부합 |
| 파일 | 로고/대표/상품/위젯 사진·Display 영상이 실제 열리고, 누락·덮어쓰기·공유 참조가 설명됨 |
| 공개/비공개 | 비공개·보관·삭제 대상이 재공개되지 않음. 복구 시점 후의 공개/삭제 변경도 별도로 대조 |
| 권한 | 소유자·허용 직원·차단 직원·비로그인/다른 매장의 읽기·쓰기, RLS/RPC/Storage grant가 의도한 범위 |
| 인증/세션/QR | 로그인·복구 경로, 세션/테이블 방문·QR 연결/만료 정책 확인. 유출 사건이면 세션/비밀키 회수 결정 포함 |
| 결제/구독 | 외부 승인/취소와 내부 원장·기간·이용권·전환 예약이 일치. 중복 청구/환불 0회 |
| 주문/호출/기기 | 접수·연결·이력과 이미 실행된 전송 결과를 대조. 과거 요청이 자동 재접수되지 않음 |
| AI/알림 | 크레딧 잔액/차감/지급과 번역 작업 상태 확인. 이미 발송된 알림을 중복 발송하지 않음 |
| 앱/예약 실행 | 복구한 스키마와 앱 revision이 호환. 각 게이트/예약의 재개 결과를 따로 확인 |

연결할 원본: [편집 저장 계약](../menu-management-save-contract.md), [구독·결제 상태 계약](../subscription-payment-state-contract.md), [스타터 번역](../starter-translations-qa.md), [위젯 파일 정리](../../lib/server/menu-widget-image-cleanup-service.ts), [현재 예약 목록](../../vercel.json).

## 훈련과 결과 기록

먼저 가상 계정·파일·메뉴·모의 결제로 격리 훈련한다. 실제 고객 백업의 복제/다운로드는 별도 승인과 접근 통제 범위가 필요하다. DB만 복구한 경우의 파일 유실, 같은 path의 교체 파일, 복구점 이후 결제, 비공개/삭제 변경, 예약/알림 재실행을 포함한다. 검증표의 각 항목은 실행일·환경·revision·PASS/FAIL/미실행·비식별 증거 위치·담당자와 함께 기록한다.

**현재 결과: 절차 작성 및 코드/공식 자료 대조 완료. 운영 설정 확인과 실제 격리 복구 훈련은 미실행.** 이 문서 작성은 백업 자동화 추가나 Production 복구 실행 승인이 아니다.
