# 아티메뉴 알림 표시·보관 정책

2026-11-03 사용자 승인. 공식 사이트 알림만 해당한다. 고객 메뉴판·주문·호출 렌더러와 별도다.

## 최근90일 표시

- `NOTIFICATION_DISPLAY_DAYS`와 `getNotificationDisplaySince`가 기준이다. 조회 시각에서90×24시간 전을 UTC ISO로 계산하며 경계 시각을 포함한다. 읽지 않은 알림도 같은 표시 범위다. 한국 시간은 표시용 날짜에만 적용한다.
- 헤더·전용 알림·마이페이지의 목록/미확인 건수와 모두 읽기가 같은 범위를 사용한다. 한 요청의 목록과 개수는 한 번 계산한 기준 시각을 공유한다. 모두 읽기는 처리 시각 이후 새 알림과90일보다 오래된 기록을 변경하지 않는다.
- 기존 조회 상한은 헤더10개, 전용/마이페이지 최신50개다. 모두 읽기는 이 상한과 무관하게 최근90일 전체 미확인 알림을 처리한다.
- 고객 안내는 표시 기준만 설명한다. “최근 90일 동안 받은 알림을 확인할 수 있습니다. 결제·구독 및 문의 내역은 각 메뉴에서 확인해주세요.” 90일이 지나면 자동 삭제된다고 안내하지 않는다.

## 생성 후1년 보관 및 정리

| 데이터 | 기준 |
| --- | --- |
| 알림 제목·본문·고객 표시용 메타데이터 | 생성 시각부터 UTC 기준1년 보관. 정확히1년인 경계는 유지하고 그보다 오래된 완료 건을 배치 정리 |
| 발송 대기·실패 기록 | `pending`/`failed`는 날짜와 재시도 횟수에 관계없이 보호. 재시도를 끝낸 실패도 운영자가 종결 상태로 확인하기 전에는 자동 삭제하지 않음 |
| 완료 상태 | `sent`/`read`/`skipped`. 읽지 않았어도 발송이 완료된 알림은 동일한 보관 기준을 사용 |
| 중복 발송 방지 최소 기록 | `notification_delivery_keys`에 원본 알림 UUID·대상 계정 UUID·매장/구독 UUID·이벤트 종류·채널·발송 식별키·상태·발송/생성 시각만 분리. 제목·본문·고객 메타데이터·이메일 주소·읽음 시각 없음 |
| 최소 기록 만료 | 같은 계정/원인에 대한 재발송 방지가 필요한 동안 유지. 기존 계정 정책에 따른 `auth.users` 실제 삭제 때 함께 제거. 탈퇴 신청만으로 기존 탈퇴 고지·재시도/보존 흐름을 바꾸지 않음 |
| 결제·구독·문의 원본 | 알림 삭제와 별도로 기존 보관 정책 유지. 정리 함수는 이 테이블들을 수정/삭제하지 않음 |

원본을 정리하려면 UUID·계정·이벤트 종류·채널·발송 식별키·상태가 일치하는 최소 기록이 있어야 한다. 누락/불일치는 자동으로 보호하고 집계에 표시한다. 매장/구독 삭제로 원본 FK가 null이 되어도 최소 기록은 기존 UUID를 유지한다.

## 구현 및 활성화

- 마이그레이션은 기존 원본 전체를 잠깐 쓰기 잠금한 뒤 최소 기록만 복사한다. 원본 행 수와 전체 필드 체크섬이 달라지거나 복사가 누락되면 트랜잭션을 중단한다. 이 이전 자체는 원본을 삭제하지 않는다.
- DB 트리거가 새 알림 키를 원자적으로 예약하며 기존 고유성 범위를 유지한다. 동시에 같은 키를 생성하면 고유 제약으로 차단된다. 상태/발송 시각 변경만 최소 기록에 동기화한다.
- 공통 `findNotificationDeliveryKey`를 모든 인앱·구독·체험·고지 생성 경로가 사용한다. 이전 전 테이블이 없을 때만 기존 조회로 대체한다. 다른 조회 오류는 재발송 없이 실패한다. 탈퇴 고지는 DB 고유 제약과 기존23505 처리로 보호한다.
- 정리는 service role만 호출 가능한 invoker RPC와 private definer 함수로 수행한다. 일반 사용자·비로그인에게 최소 기록 조회/정리 실행 권한을 주지 않는다. 기존 알림 RLS를 유지한다.
- `/api/cron/prune-notifications`는 CRON_SECRET Bearer 인증을 요구한다. 환경값 `ENABLE_NOTIFICATION_RETENTION_EXECUTE=true`인 Production만 실제 실행하며, 미설정·Preview는 모의 실행이다. `?dryRun=true`는 활성화 여부와 관계없이 강제로 모의 실행한다.
- 매일 UTC20시(한국시간 다음날05시) 실행한다. 요청당100건, DB 상한500건이다. DB 서버의 현재 시각을 쓰며 호출자가 임의의 미래 기준일을 주입할 수 없다. 정리 호출을 직렬화하고 처리 중인 행은 잠금으로 보호한다.
- 반환/로그는 기준일·후보/삭제 건수·보호 건수만 포함한다. 제목·본문·수신 주소를 반환하지 않는다. 상세 운영 절차는 `runbooks/notification-retention-rollout.md`를 따른다.

백업 복사본은 기존 백업 만료 정책을 따른다. 이 작업은 백업을 새로 만들거나 백업 내역·회원 탈퇴·법정 원본 보관 정책을 변경하지 않는다.
