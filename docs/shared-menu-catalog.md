# 메뉴판 간 메뉴 가져오기·연결 계약

최종 갱신: 2026-08-28

## 목적

한 Owner 계정이 디스플레이 메뉴판의 메뉴 내용을 새 다이닝 메뉴판으로, 또는 반대 방향으로 다시 입력하지 않고 가져올 수 있게 한다. 사용자는 가져오기 시 두 방식 중 하나를 명시적으로 선택한다.

- `연결 유지`: 기존의 대응 메뉴에 한해 공통 메뉴 정보를 양방향 동기화한다.
- `독립 복사`: 현재 내용을 한 번 복사하고 이후에는 각 메뉴판을 독립적으로 편집한다.

기존 메뉴판은 자동 연결하거나 변환하지 않는다. Owner가 작성중 메뉴판에서 가져오기를 실행한 경우에만 새 계약을 사용한다.

## 연결되는 정보

- 카테고리명·설명
- 메뉴명·설명·기본 가격·가격 문구
- 공개 이미지 URL
- 배지·추천·품절·원산지·알레르기 등 메뉴 공통 문구
- 기존 JSON 번역과 locale별 카테고리·메뉴 번역

연결은 가져오기 시 만들어진 대응 카테고리·메뉴 행 사이에서만 동작한다. 이후 어느 한 메뉴판에서 새 메뉴를 추가하거나 삭제하는 작업은 다른 메뉴판에 자동으로 추가·삭제하지 않는다.

## 메뉴판별로 유지되는 정보

- 메뉴 추가·삭제, 페이지 구성, 카테고리·메뉴 배치와 정렬
- 페이지·카테고리·메뉴 노출 여부와 template별 디자인
- 가격 옵션·가격 열·맛과 특징 지표
- 타임세일과 위젯
- 주문 가능 여부와 주문 옵션
- 다이닝·디스플레이별 기능 entitlement와 공개 상태

가져오기 시 가격 옵션·가격 열·특징 지표는 최초 복사하지만 이후 연결 동기화에는 포함하지 않는다. 타임세일·위젯·주문 설정은 대상 메뉴판의 기존 내용을 제거하고 원본에서 복사하지 않는다.

## 안전 경계

- 인증된 Owner가 소유한 두 메뉴판 사이에서만 실행한다. 직원은 가져오기와 연결 해제를 실행할 수 없다.
- 대상은 반드시 `draft` 상태여야 한다. 공개·보관 메뉴판은 덮어쓰지 않는다.
- 원본과 대상이 같으면 거부한다.
- 가져오기는 한 DB transaction과 target advisory lock 안에서 수행한다.
- 대상의 기존 페이지·카테고리·메뉴·타임세일·위젯은 명시적 확인 문구 입력 후에만 교체한다.
- 연결 trigger는 같은 `menu_sites.user_id`의 공유 ID만 갱신해 다른 계정으로 전파되지 않는다.
- 연결된 메뉴판에서 공통 정보를 편집할 수 있는 직원은 같은 Owner의 대응 메뉴 정보에도 영향을 줄 수 있음을 UI에 알린다.
- 대상의 `image_path`는 원본 Storage 경로를 소유한 것처럼 복제하지 않고 null로 둔다. 공개 이미지 URL만 연결한다.
- 이미지 URL 의존성과 연결 무결성을 보호하기 위해 활성 연결 양쪽 메뉴판의 hard delete를 DB에서 차단한다. 대상에서 연결을 해제한 뒤에만 어느 쪽이든 영구 삭제할 수 있다.
- `menu_site_content_links`는 RLS를 적용하고 anon 접근을 허용하지 않는다.
- generated Supabase types는 migration을 Production에 적용한 뒤 공식 생성 절차로만 갱신한다.

## 사용자 흐름

1. 새 다이닝 또는 디스플레이 메뉴판을 작성중 상태로 만든다.
2. 편집 화면의 `메뉴 가져오기`를 연다.
3. 같은 계정의 원본 메뉴판을 고른다.
4. `연결 유지` 또는 `독립 복사`를 고른다.
5. 교체 범위를 확인하고 `메뉴 가져오기`를 입력한다.
6. 연결 유지인 경우 같은 화면에서 `연결 해제`를 입력해 언제든 독립 상태로 전환할 수 있다. 현재 내용은 보존된다.

## 적용 순서

1. migration을 별도 환경에서 검증한다.
2. Production 적용 전 read-only precheck와 사람 승인을 받는다.
3. `20260828040033_add_shared_menu_catalog.sql`을 1회 적용한다.
4. 테이블·RLS·trigger·RPC grant postcheck를 수행한다.
5. generated Supabase types를 다시 생성하고 수동 변경이 없는지 확인한다.
6. Owner 테스트 계정의 기존 원본과 새 draft 대상에서 독립 복사·연결·연결 해제를 각각 1회 QA한다.

Production migration 전에는 UI와 서버 action을 배포하지 않는다. RPC가 없는 상태에서 버튼을 노출하면 사용자에게 실패 화면을 제공하게 되므로 migration과 애플리케이션 배포를 같은 승인된 rollout으로 묶는다.
